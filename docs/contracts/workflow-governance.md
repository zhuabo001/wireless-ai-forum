# 工作流资产治理契约

## 目的

本契约定义项目级 AI 工作流资产的职责、授权边界和完成语义。每条规则只在一个权威位置定义；其他资产只负责路由。

## 资产职责与迁移

| 当前内容或资产 | 权威目标 | 处理方式 |
| --- | --- | --- |
| 项目定位、技术栈、架构、关键目录 | 根 `CLAUDE.md` | 精简为所有任务都需要的项目心智模型 |
| plan-progress-commit-record 完整流程 | `.claude/skills/close-development-loop/` | 按需加载，根文件只保留路由 |
| Vue 组件设计规则 | `.claude/rules/vue.md` | 仅在处理 `**/*.vue` 时加载 |
| TypeScript 类型设计规则 | `.claude/rules/typescript.md` | 仅在处理 `**/*.{ts,vue}` 时加载 |
| 可机器判断的 Vue、TypeScript 和构建约束 | ESLint、`vue-tsc`、Vite build | 通过 `npm run check` 统一执行 |
| 自动导入 globals | `.eslintrc-auto-import.json` | 继续由现有生成机制维护，由 ESLint Flat Config 消费 |
| Playwright 测试生成与执行流程 | 现有项目级 Playwright Skills | 保持独立，不并入通用需求闭环 |
| 一次性历史、调试记录、动态记忆 | `records/`、研究文档或外部 memory | 不进入根 `CLAUDE.md` |
| 特定转换或一次性专项流程 | 独立 Skill 或普通文档 | 不由根文件常驻路由 |

## 任务分级

| 等级 | 判定 | 必需资产 | 完成要求 |
| --- | --- | --- | --- |
| L0 | 解释、研究、诊断、审查 | 无 plan/progress | 给出有证据的结论，不修改或提交 |
| L1 | 明确、低风险、局部修改 | plan 可选，progress 不需要 | 实施修改并运行匹配验证 |
| L2 | 多文件功能或多个验收条件 | plan、progress | 逐里程碑实施、验证并记录证据 |
| L3 | 公共接口、数据、安全或不可逆操作 | plan、progress、额外确认 | 独立验证，高影响动作单独授权 |

## 高影响动作授权

授权只覆盖明确动作和明确范围，不自动向后续动作扩张。

| 动作 | 普通实现请求 | 显式调用 `close-development-loop` | 额外授权要求 |
| --- | --- | --- | --- |
| 读取、编辑任务范围文件 | 允许 | 允许 | 无 |
| 运行格式化、lint、类型检查、测试和构建 | 允许 | 允许 | 无 |
| 创建 plan、progress、record | 仅任务需要时 | 允许 | 不覆盖既有用户文件 |
| 创建本地 commit | 默认不允许 | 验证通过后允许提交任务范围增量 | 脏工作区必须精确暂存 |
| 创建或切换分支 | 默认不允许 | 默认不允许 | 用户明确指定 |
| push | 不允许 | 不允许 | 用户明确指定目标分支和远端 |
| 创建或更新 PR | 不允许 | 不允许 | 用户明确要求 |
| merge、删除分支或其他不可逆操作 | 不允许 | 不允许 | 用户明确要求并再次确认目标 |

## 交付证据

一个里程碑只有同时满足下列条件才能标记完成：

1. 变更范围与计划或用户需求一致。
2. 已执行与变更匹配的验证，并记录命令、结果与未验证项。
3. 验证失败已解决；无法解决时保持未完成并记录阻塞。
4. 未覆盖、清理或提交任务范围外的用户修改。
5. 对缺陷修复，失败事实、诊断假设、已验证根因和回归证据相互区分。

最终完成还需要独立检查需求符合性和变更质量。环境支持独立代理时使用独立代理；否则使用独立验证清单，并明确说明验证方式。

## 事实与不确定性

- 将仓库内容、用户陈述和工具结果作为事实来源。
- 将推断明确标记为推断，不把未经验证的联系描述为事实或根因。
- 先使用仓库和工具查证；仅当剩余歧义会改变范围、接口、数据、安全或不可逆动作时询问用户。
- 轻微歧义使用明确假设继续，并在交付中披露。

## 验收标准

- 每项现有规则有唯一目标位置或明确废弃理由。
- 根 `CLAUDE.md` 不包含多步骤 SOP、局部代码规范或动态记忆。
- Skill 的触发描述只描述任务、输入和结果，不依赖 Agent 品牌或工具身份。
- `npm run check` 是项目级统一质量入口。
- L0/L1 不会误触发正式闭环，L2/L3 的完成状态可以追溯到证据。
- commit、分支、push、PR 和 merge 的授权不会相互隐式扩张。
