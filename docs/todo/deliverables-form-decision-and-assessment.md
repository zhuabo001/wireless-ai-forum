# 难题英雄榜：交付件形态、验收标准与评审机制设计

日期：`2026-09-04`

状态：设计建议待确认 —— 「评分人是谁」存在未决问题（见文末），确认后可立项实施。

## 现状：交付件目前是「不存在」的

核查三个关键位置：

- **`ProgressDialog.vue:15-20`** — 揭榜人只能选阶段（方案设计中 20% → 方案已提交待发布者确认 50% → 试点验证中 75% → 申请验收待发布者结题 90%）+ 填一段 `note` 文本。**没有交付物字段**：无链接、无附件、无代码仓引用。
- **`docs/api/challenges-api.md:107-109`** — `POST /progress` 请求体只有 `{ stage, percent, note }`，整个接口表里没有任何交付物、验收、结题相关的端点。
- **`ChallengeFloatingActions.vue:27-41`** — 发布者只有置顶/删除/编辑三个动作，**没有「确认方案」「验收」「结题」按钮**。状态机里 `closed`（已结题）这个状态目前没有任何路径可以到达。

所以现状是：进度更新只是**状态广播**（告诉围观者"我做到哪了"），不是交付。同时阶段名已经承诺了两个评审动作（"待发布者确认"、"待发布者结题"），但发布者侧对应的确认/验收能力完全缺失——这是设计稿留下的一个未闭环的承诺。

## 设计建议

### 1. 交付件是什么？

交付件形态取决于题目类别，建议建模为**挂在进度节点上的交付物**，而非一个独立大实体：

```ts
interface ChallengeDeliverable {
  type: 'link' | 'repo-pr' | 'text'   // 方案文档链接 / 代码仓 PR / 富文本说明
  uri?: string                        // type 为 link/repo-pr 时的地址
  contentHtml?: string                // type 为 text 时的正文
  description: string                 // 一句话说明交付内容
  submittedAt: string
}
```

不同阶段交付物不同：50% 节点交付的是**方案文档**（链接或富文本），90% 节点交付的是**验证报告/成果**（试点数据、PR 链接）。所以交付物应该长在 `timeline` 条目上，让 ProgressDialog 在选择 50%/90% 阶段时要求附交付物。

### 2. 通过什么途径交付？

两选一，结合当前「纯前端 + MSW、无真实后端」的现状：

- **链接引用（推荐先做）**：交付物托管在既有系统（内部知识库、代码仓、文档平台），揭榜人只提交 URL + 说明。零存储成本，与 mock 现状匹配，真实后端落地时也无需文件服务。
- **附件上传**：需要对象存储后端，当前阶段不具条件，不建议先做。

### 3. 如何判断交付件符合要求？

这是比交付件更根本的缺口：**发题时根本没有填「验收标准」**。`ChallengeFormData`（`src/types/pageDesign/challengeHeroes.ts:133-139`）只有标题/类别/部门/难度/正文，没有验收标准字段。没有标准，评审就只能是发布者拍脑袋。

建议在发布表单增加**「交付要求与验收标准」**必填字段（例如：需提供可复现的方案文档 + 试点环境一周验证数据，掉线率降至 X% 以下），在详情页对揭榜人可见。评审时发布者对照该标准逐项判断。

### 4. 评审机制是什么？

阶段名已经隐含了一个两级评审流，建议把它显式化：

| 节点 | 评审动作 | 评审人 | 通过 | 驳回 |
| --- | --- | --- | --- | --- |
| 50% 方案已提交 | 确认方案 | 发布者 | 进度推进，可进入试点 | 退回 20% + 驳回理由入时间线 |
| 90% 申请验收 | 验收结题 | 发布者 | 状态 → `closed`，悬赏分结算给揭榜人 | 退回 75% + 整改意见 |
| 争议 | 仲裁 | 超管 | 单方无法推进时介入 | — |

驳回必须填理由并写入时间线留痕（与取消揭榜的 `reason` 机制一致）。结题动作是悬赏分实际入账的触发点，这也是「得分总榜」数据的真实来源。

### 5. 是否需要面向评分人的独立评审页面？

**现阶段不建议做独立页面**，理由：

- 评审人是发布者本人（不是第三方评分人），评审上下文就是题目本身——详情页就是最合适的评审场所。在发布者视角下，时间线的「待确认」节点旁内联放「确认方案 / 驳回」「验收结题 / 驳回」按钮 + 一个驳回理由 dialog，即可闭环，工作量小且不增加信息架构。
- 真正值得做独立入口的是**待办聚合**：当发布者同时发了多道题，需要一个"待我评审"清单。这不需要新页面——复用 challenges 列表页，加一个 `pending-review` tab（我的发布 + 有待确认节点的题）即可，接口侧只是列表查询多一个过滤条件。

## 未决问题（阻塞立项）

- [ ] **「评分人」指的是谁？** 当前模型里只有**超管定悬赏分**（`ScoreDialog`，题发布时定分）和**发布者验收**两个角色。如果业务上设想的是「专家评审团对交付质量打分、按分分配悬赏」这类第三方评审机制，那才需要独立的评审工作台页面——但这会改变领域模型（评审人、评审单、打分维度），属于一个新的 L2/L3 需求，需先确认再立项。

## 落地优先级建议

1. **验收标准字段**（发布表单 + 详情页展示）——没有它评审无据可依
2. **交付物挂到进度节点**（ProgressDialog 在 50%/90% 阶段要求附链接/文本）
3. **发布者确认/验收/驳回动作**（详情页内联，打通 `closed` 状态）
4. **列表页「待我评审」tab**（发布者聚合待办）
5. （待定）第三方评审团工作台——取决于上面「评分人是谁」的答案

前四项是对现有设计的补全，量级约一个 L2 里程碑；确认后可先出计划文档再实施。
