## 一、评审结论

### 做得对的地方（值得保持的资产）

1. **测量纪律是本套工作的核心资产**：先基线后动手、归因先行（sourcemap-explorer 字节级归因否决了「246KB EP 是首页负担」的直觉——实际首页只用 15KB）；P0（全站静态 3.43MB→435KB，-87%）是体检流程抓出的配置级 bug，价值在流程而非修复本身。
2. **诚实处理 null 结果**：M2「优化后慢 16ms」不掩饰、三轮复测坐实 ±120ms 噪声带、只宣称确定性收益；M3 用对照实验否决自身假说并判明「剩余空间 ≤10ms」；M5 帖子页 -1% 如实报告。防后人重复投入的价值 > 成功记录。
3. **停止纪律**：M3 判决后转 INP 而非硬抠布局；M3b 量化动画 0.9ms/帧后按视觉保真约束判「不动」。
4. **A/B 可信度**：worktree + node_modules 符号链接保证基线与 HEAD 依赖逐字节一致；M5 验证「节流放大 3-4 倍」预测（实测 2.5-4.2x）——预测可被事后验证说明测量协议自洽。
5. **回归防线雏形**：verify-build 懒加载边界校验并入 `npm run check`。

### 等真实后端/上线后

1. **网络层**：preconnect 到 API origin；后端 ETag/304 条件请求（与 `docs/todo/vue-query-real-backend-roadmap.md` L3 探测器呼应——探测器便宜与否取决于后端是否给 304）；CDN 静态资源。现状 TTFB 13ms，本环境不可测，不必现在做。
2. **最简 RUM**：web-vitals + 采样上报——唯一能坐实冷字体地板（R4 闭环）与真实网络 chunk 传输成本的途径，也是 S6 预取的验收手段。
3. **vue-query 推广其余模块**（roadmap 已立项）：forum/courses 等裸 fetch 换查询层，请求级收益在真实后端下完整。
4. **图片线从零建**：真实内容引入图片后，尺寸分级 / avif/webp / 懒加载 / `decoding=async` 才有着力点。
5. **内容页预渲染评估**（`docs/todo/ssr-refactor-todo.md` 已铺路）：若走 SSR/预渲染，IO 懒加载架构的「首屏空壳 + 客户端挂载」逻辑需整体重审——架构级，单独立项。

## 三、总体判断

最大亮点不是「LCP -43%」，而是证明了哪些数字不值得追求（≤10ms 地板、噪声带、冷字体不可消除），且每份记录都能让后人知道「为什么停在这里」。真正短板是**防守性不足**：战果依赖一次性的边界检查，新页面/新依赖/移动端三个变量没有持续守卫。**S1 + S2 是最推荐优先立项的两项**——把已取得的胜利变成常态的最小成本动作。
