# 工作流资产重构优先级（Claude-first）

## 目标与边界

本轮以 Claude Code 为主要开发执行工具，建立简洁、可验证、按需加载的工作流资产体系。

- 本轮重构范围：`CLAUDE.md`、`.claude/rules/`、`.claude/skills/`、质量检查命令与后续 CI。
- 本轮不修改 `AGENTS.md`。该文件当前承载 claude-mem 上下文，不应在未确认其生成机制前覆盖、导入或迁移。
- 现有未提交文件属于开发者工作区状态；重构过程不得覆盖、清理或混入无关提交。
- 规则的单一事实来源：每条约束只能在一个权威位置定义，其他位置只做路由或引用。

本计划吸收以下五项设计原则：

1. 用简洁的项目定位、架构和数据流帮助 Agent 建立项目心智模型。
2. 将工作要求表达为可验证的交付契约，每个阶段都有明确产物和证据。
3. 为机器检查建立统一质量入口，避免 Agent 每次重新组合验证命令。
4. 调试时先建立失败证据与根因假设，再修复并执行回归验证。
5. 对 commit、分支切换、push、PR、merge 等高影响动作设置明确授权边界。

## 优先级总览

| 优先级 | 阶段 | 目的 | 主要产物 |
| --- | --- | --- | --- |
| P0 | 固化治理边界 | 明确资产作用域、兼容边界和保护规则 | 重构映射与验收标准 |
| P1 | 重写需求闭环契约 | 消除现有流程语义冲突 | 任务分级、提交与完成语义 |
| P2 | 盘点并收敛机器质量门禁 | 复用现有工具并将可判定规则下沉 | 工具盘点、项目级 ESLint 配置、统一 `check` 命令 |
| P3 | 创建需求闭环 Skill | 把正式需求的多步骤流程按需加载 | `close-development-loop` Skill 与模板 |
| P4 | 拆分路径规则 | 让 Vue/TypeScript 规则只在相关文件任务中生效 | `.claude/rules/` |
| P5 | 瘦身根 `CLAUDE.md` | 让根文件成为项目契约与路由入口 | 精简的项目级 `CLAUDE.md` |
| P6 | 对抗性验证与试运行 | 证明路由和门禁按预期工作 | 场景测试记录与改进项 |

## P0：固化治理边界

### 决策

采用 Claude-first：先把 Claude Code 的资产体系稳定下来，后续另开任务调查 claude-mem 与 `AGENTS.md` 的关系，再决定是否建立跨 Agent 的共享契约。

### 要完成的工作

1. 列出当前 `CLAUDE.md`、已有 Playwright Skills、`docs/` 与 `records/` 的职责。
2. 建立“当前内容 → 目标位置”的迁移表，避免规则复制。
3. 明确用户级、项目级、路径级、Skill、工具配置的边界。
4. 为本次重构定义验收标准与非目标。
5. 盘点现有质量工具，区分直接依赖、传递依赖、配置文件和可执行命令，避免重复引入或误判能力。
6. 建立高影响动作授权表，明确普通开发请求、显式闭环调用与单独用户授权分别允许哪些 Git/GitHub 动作。

### 完成标准

- 所有现有规则都有唯一目标位置或明确废弃理由。
- `AGENTS.md` 不在本轮修改范围内。
- 已识别并保留工作区中与任务无关的未提交内容。
- 已有工具能力和缺口都有仓库证据，不以依赖名称或可执行文件是否存在代替可用性验证。
- commit、分支切换、push、创建或更新 PR、merge 的授权边界没有歧义。

## P1：重写需求闭环契约

这是整个重构的地基。应先定义流程语义，再写 Skill 或移动文档。

### 任务分级

| 等级 | 典型任务 | 是否需要计划 | 是否需要 progress | 是否默认提交 |
| --- | --- | --- | --- | --- |
| L0 | 解释、研究、诊断、代码审查 | 否 | 否 | 否 |
| L1 | 明确、低风险的小修改 | 可选 | 否 | 否 |
| L2 | 多文件功能、多个验收条件的正式需求 | 是 | 是 | 仅在调用闭环流程或用户明确授权后 |
| L3 | 公共接口、数据模型、安全边界、不可逆操作 | 是 | 是 | 额外确认与独立验证 |

### 必须解决的冲突

1. 取消“任何代码开发都必须先有 `plan.md`”的绝对要求；L0/L1 不应被强制走正式闭环。
2. 明确调用 `close-development-loop` 是否构成创建 commit 的授权；默认普通开发请求不自动提交。
3. 消除 progress 中记录自身 commit hash 的循环依赖。progress 应记录状态和验证证据；完整 commit 列表写入最终 record。
4. 明确失败语义：验证失败、范围不清、依赖缺失时，不得标记任务完成或进入下一阶段。
5. 将“启动 verification-agent”改为能力无关的独立验证要求：环境支持时使用独立代理，否则使用独立验证清单。
6. 定义最小交付证据：变更范围、执行过的验证命令、验证结果、未验证项和剩余风险；不能只用“已完成”作为完成依据。
7. 为缺陷修复制定根因纪律：先建立可复现现象或其他失败证据，再区分事实、假设与根因结论；可自动复现时优先补充回归测试。
8. 将 commit、切换分支、push、创建或更新 PR、merge 视为独立的高影响动作，不因普通“实现需求”请求自动获得授权。

### 完成标准

- 任意任务可被稳定分流至 L0–L3。
- 提交、验证、状态更新和恢复路径没有循环或授权歧义。
- 正式需求的“完成”有可检查的证据定义。
- 缺陷修复不能在没有失败证据和根因验证的情况下宣称已解决。

## P2：盘点并收敛机器质量门禁

Skill 不应承诺执行仓库中不存在的验证命令，也不应重复引入已经存在的能力。先确认现状和缺口，再收敛工具入口。

### 已确认现状

- `package.json` 已有 `build` 脚本，并直接依赖 `vue-tsc` 与 `vue-doctor`。
- `vue-doctor` 的传递依赖带入了 ESLint 9 和 `vue-eslint-parser`，当前工作区存在 ESLint 可执行文件。
- `.eslintrc-auto-import.json` 已提供自动导入全局变量清单，但它不是完整的项目级 ESLint 配置。
- `package.json` 尚无 `lint`、`type-check`、`check` 脚本，也没有直接声明 ESLint、`eslint-plugin-vue` 或 TypeScript ESLint 集成依赖。
- 仓库当前没有项目级 `eslint.config.*`；因此“存在 ESLint 二进制”不等于“已经具备稳定可维护的项目 lint 门禁”。

### 要完成的工作

1. 验证 `vue-tsc`、`vue-doctor`、Vite build 和传递引入的 ESLint 各自覆盖什么问题、退出码是否稳定，以及是否适合进入默认门禁。
2. 在确有缺口时补充项目级 ESLint Flat Config，接入 Vue、TypeScript 和现有自动导入 globals；不要依赖 `vue-doctor` 的传递依赖作为长期项目 API。
3. 只添加项目实际需要的直接依赖，并记录新增理由；不重复安装已有且版本满足要求的工具。
4. 为 `package.json` 建立统一入口，目标形态为：

   ```json
   {
     "lint": "eslint src --max-warnings=0",
     "lint:fix": "eslint src --fix",
     "type-check": "vue-tsc --noEmit",
     "check": "npm run lint && npm run type-check && npm run build"
   }
   ```

5. 将可自动判断的约束迁移到工具：Vue 模板错误、显式 `any`、未使用变量、TypeScript 类型问题等；是否纳入格式化检查要根据现有风格和误报情况决定。
6. 评估 `vue-doctor` 是否作为手动诊断命令或独立脚本保留，不在未确认稳定性和职责边界前把它强行加入 `check`。
7. 根据项目实际需要再决定是否加入 Prettier、Stylelint 与 GitHub Actions；不要在未验证收益前增加门禁。

### 完成标准

- `npm run check` 可在干净环境中作为统一质量入口运行。
- ESLint 等门禁依赖由项目直接声明，不依赖其他工具偶然带入的传递依赖。
- 新配置复用现有自动导入 globals，不与已有生成机制冲突。
- 可机器验证的规则不再仅依赖 `CLAUDE.md` 自然语言约束。
- 新门禁不与 Tailwind、Sass、自动导入或既有构建流程冲突。

## P3：创建 `close-development-loop` Skill

### 目标结构

```text
.claude/skills/close-development-loop/
├── SKILL.md
├── agents/openai.yaml
└── assets/
    ├── progress-template.md
    └── record-template.md
```

### Skill 核心流程

```text
任务分级
→ 定位或确认规格
→ 创建进度面板（仅 L2/L3）
→ 实施当前里程碑
→ 运行匹配的验证
→ 更新状态与验证证据
→ 按授权创建里程碑提交
→ 独立验证
→ 请求人工验收
→ 创建最终 record
```

### 设计原则

- 第一版以显式调用为主，避免小修改意外创建 plan、progress 或 commit。
- Skill 的 `name`、`description` 与触发条件必须保持 Agent-neutral：以任务类型、输入工件和所需结果描述触发场景，不得写入“当 Codex/Claude 使用时”等工具身份条件。不同 Agent 的工具能力、目录约定或降级策略仅在 Skill 正文的执行阶段处理。
- `SKILL.md` 只保留流程、分流条件与完成条件；模板放入 `assets/`。
- 每个里程碑必须定义输入、产物、验证方式和完成证据；Skill 只引用统一质量入口，不复制工具内部命令清单。
- 缺陷修复先记录失败证据和根因假设；修复后使用相同证据或回归测试证明问题消失，不得将未经验证的推测写成根因。
- commit、分支切换、push、PR 和 merge 分别检查授权，不把调用 Skill 自动解释为所有外部动作的授权。
- 如出现大量机械校验，再补充 validator 脚本；不要过早脚本化。
- 创建时使用标准初始化方式，并运行 Skill 结构校验。

### 完成标准

- Skill 能从计划、用户需求或现有文档中建立可审计闭环。
- 未授权提交、失败验证、脏工作区、缺失计划等边界都有明确处理。
- 每个已完成里程碑都能追溯到产物和验证证据，失败项与未验证项不会被完成状态掩盖。
- 缺陷修复记录能区分失败事实、诊断假设、已验证根因和回归证据。
- Skill 通过结构校验，并用真实或模拟任务 forward test。

## P4：拆分路径规则

### 目标结构

```text
.claude/rules/
├── vue.md
└── typescript.md
```

### Vue 路径规则

作用域为 `**/*.vue`，只保留不能可靠自动化的设计判断：组件拆分边界、Props/Emits 设计、局部状态与 Pinia 的选择、展示组件与业务组件的界线。

### TypeScript 路径规则

作用域为 `**/*.{ts,vue}`，强调公共边界、外部输入、复杂返回值等位置的类型质量；不再要求对可安全推断的局部变量逐一标注类型。

### 完成标准

- Vue/TypeScript 规则不会污染非前端任务的常驻上下文。
- 每项规则要么由工具执行，要么由路径规则或 Skill 承载。

## P5：瘦身根 `CLAUDE.md`

在所有目标资产已经存在并验证后，最后改写根文件，避免出现失效链接或未实现的命令。

### 根文件应保留

1. 项目定位、技术栈、精简架构和核心数据流，帮助 Agent 快速建立项目心智模型。
2. 最重要的模块入口和关键目录，不复制完整目录百科。
3. 关键架构边界和团队级约定。
4. 统一验证命令及其适用范围。
5. 事实、证据与不确定性处理的项目级简述。
6. 指向路径规则和 Skills 的短路由。
7. 明确的不可破坏约束，以及 commit、分支切换、push、PR、merge 的授权边界。

### 根文件不应保留

- 完整的 plan-progress-commit 逐步 SOP。
- Vue/TypeScript 的完整细则。
- 可由 lint、类型检查、测试或 CI 判定的规则。
- 一次性历史、调试笔记或动态 memory。

### 完成标准

- 根 `CLAUDE.md` 成为“项目契约与导航”，而不是百科或操作手册。
- 内容目标控制在约 60–100 行，保持简洁、可验证，并且没有重复定义。
- 新会话无需遍历完整仓库即可从根文件理解“项目是什么、主要数据如何流动、从哪里开始验证”。
- 所有 Skill、规则、命令和引用都真实存在。

## P6：对抗性验证与试运行

用下列场景验证资产是否真正能稳定分流：

1. 只读解释代码：不创建 plan、不修改文件、不提交。
2. 修改一处明确文案：直接实施并验证，不启动完整闭环。
3. 多文件正式功能：定位或请求计划，并创建 progress。
4. 验证失败：不能将对应步骤标记完成。
5. 已有未提交用户修改：不覆盖、不混入无关提交。
6. 未明确授权 commit：不自行提交。
7. 无法验证事实：区分事实、推断与假设；仅重大歧义才询问用户。
8. 缺陷尚不能复现：先收集失败证据并验证根因假设，不直接尝试随机修复。
9. 未明确授权 push、创建 PR 或 merge：不执行相应外部动作，且不把其他 Git 授权扩大解释。

### 最终验收标准

- 每条规则只有一个权威来源。
- 根 `CLAUDE.md` 不再包含多步骤 SOP。
- Skill 与路径规则按任务和文件范围正确加载。
- `npm run check` 通过。
- 需求闭环可以完成，且不会误触发在 L0/L1 任务上。
- 不存在规则冲突、无效引用或历史 memory 混入项目契约。
- 项目心智模型、交付证据、统一质量入口、根因纪律和高影响动作边界均通过对应场景验证。

## 推荐实施提交顺序

```text
1. docs: define workflow execution contract
2. chore: consolidate lint and type-check gates
3. feat: add close-development-loop skill
4. docs: add scoped Vue and TypeScript rules
5. refactor: slim project CLAUDE.md
6. test: validate workflow assets and routing
```
